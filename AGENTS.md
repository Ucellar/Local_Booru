# Local Booru — правила для ИИ-агентов и людей, которые работают над программой вместе с владельцем

Закрытый репозиторий `Ucellar/Local_Booru_dev` — полный код программы владельца (Ucellar). Над ним работают двое:
владелец со своим ассистентом (Claude) и друг владельца (Rootolk) со своим ИИ-агентом. Публичная копия программы —
`Ucellar/Local_Booru`: в неё ничего не отправлять (её собирает `tools/publish_public.py` из этого кода, только
владелец).

## Прочитать перед первой правкой
1. Этот файл.
2. `CLAUDE.md` — память проекта: что за программа, как устроена, где что лежит, правила и «ловушки» (тронешь X —
   сломается Y). Раздел «Работа на компьютере владельца» — про его компьютер: пути `F:\…`, `E:\…`, скрипты
   `tools/pc/`, запрет git в смонтированной папке — это для его ассистента. У вас своя копия репозитория, git в ней
   обычный.
3. `docs/map/README.md` — карта кода; `CHANGELOG.md` — что менялось в последних версиях и почему.

## Ветки
- `main` — то, что стоит у владельца. Напрямую в него не коммитить и не пушить.
- Каждая задача — своя ветка от свежего `main`, имя `friend/<коротко-о-задаче>` (латиницей, через дефис):

      git fetch origin
      git switch -c friend/reader-zoom origin/main

- Коммиты небольшие, в сообщении — что сделано и зачем (можно по-русски). Отправить ветку:
  `git push -u origin friend/<задача>`.
- Готово — Pull Request в `main` (на GitHub или `gh pr create --base main --fill`). В описании: что сделано, где это
  увидит владелец (какая страница, какая кнопка), какие проверки прошли и какие не запускались.
- Пока PR открыт, `main` может уйти вперёд — подтянуть его: `git fetch origin && git rebase origin/main`, затем
  `git push --force-with-lease` (только в свою ветку, никогда в `main`).
- В `main` ветки вливает сторона владельца: его ассистент смотрит ветку, прогоняет все проверки, ставит её владельцу
  на компьютер и даёт номер версии с записью в `CHANGELOG.md`. Номер версии в своей ветке не менять,
  `CHANGELOG.md` можно не трогать — всё нужное в описании PR.

## Чтобы не мешать друг другу
- Договориться, кто что делает: одна часть программы — один человек. Если правка задевает чужую часть — сказать об
  этом в PR.
- Скачивание видео с сайтов (`core/video_download.py`, `video_hls.py`, `video_sources.py`, `video_dubs.py`,
  `fmp4_mux.py`, `video_episodes.py`, `webui/pages/video_get.py` и их проверки) — зона отдельного чата владельца:
  не удалять, не откатывать, поведение скачивания не менять (подробно — в `CLAUDE.md`).
- Без нужды не переименовывать и не переносить файлы — это самый частый источник конфликтов.

## Нельзя
- Класть в репозиторий ключи, логины, пароли, cookies, токены, свои пути и имя пользователя. Настройки и данные
  программы живут вне папки кода (в архиве, на который указывает `local_booru_workspace.json`; он в `.gitignore`).
- Проверять на настоящей библиотеке: проверки работают только во временных папках (см. ниже).
- Покупать или обходить платные главы и видео, DRM, капчи; добавлять плееры и сайты, о которых владелец не просил
  (его правила — в `CLAUDE.md`).
- Пушить в публичный `Ucellar/Local_Booru` и выпускать релизы — это только владелец.

## Проверки
Python 3.11, библиотеки — `requirements.txt` (точные версии — `requirements.lock.txt`). Проверки никогда не трогают
настоящий архив и не ходят на настоящие сайты: каждая берёт временную папку данных, сайты — свои, на 127.0.0.1.
- Всё сразу: `python tools/dev_checks/run_checks.py` (долго, до часа).
- Только нужные: `python tools/dev_checks/run_checks.py static manga_archive.py webui_smoke.py` — `static`
  (синтаксис, импорты, вызовы между модулями) и перечисленные файлы из `tools/dev_checks/`.
- Новая возможность — новая проверка в `tools/dev_checks/` (по образцу соседних) и её имя в списке `run_checks.py`.
- Страницы проверяются и в браузере, если стоят Playwright с Chromium (`pip install playwright`,
  `playwright install chromium`).

## Владелец
Владелец не программист: код он не читает, а запускает программу и пишет, что не так. Его ассистент проверяет вашу
ветку, ставит её ему на компьютер и рассказывает простыми словами, что изменилось. Поэтому в описании PR важнее всего,
что увидит владелец, а не только что поменялось в коде.
